DECISIONS.md A living log of key decisions made during the rebuild of the training app. Captures what was decided, what was considered, and why.

ARCHITECTURAL DECISIONS
One central brain, tabs are lenses Decided: March 2026
The v1 app had separate AI context built per route — each tab assembled its own prompt, loaded its own data, and had its own view of the athlete. This created fragmented intelligence where decisions made in one tab didn't propagate to others.
We chose a single central context builder that every tab draws from. The brain is identical regardless of tab. The only thing that changes per tab is a single focused instruction about what the athlete is trying to do right now.
Rejected: separate brains per tab, tab-specific context assembly, different tool availability per tab as a primary differentiator.

Natural language over structured fields for athlete profile and preferences Decided: March 2026
Early thinking pushed toward a structured signals table — extracting discrete facts from conversations and storing them as queryable fields. Categories like "travel flags", "fatigue observations", "performance trends."
We rejected this because structure limits what the AI can notice. If we define the categories upfront, we're making decisions about what matters before the AI has a chance to observe what actually matters for this specific athlete. Natural language preserves the full fidelity of what was said and lets the AI reason across it freely.
The magic moment that informed this: pasting a full chat log into Claude and getting sharp, specific insights — that happened because the AI had access to rich unstructured context, not structured fields.
Structured data is kept only where it genuinely needs to be: training numbers (sets, runs), dates, and UI-renderable plan structures.
Rejected: signals table, structured attribute extraction, predefined category taxonomy.

Principles not rules in the prompt Decided: March 2026
V1 had hardcoded rules: "NEVER squat heavy within 48 hours of a tempo run", "One lower session per week while running 3x", specific HRV thresholds with prescribed responses. These created rigid, deterministic behaviour that felt mechanical rather than intelligent.
We replaced rules with principles — teaching the AI why certain sessions conflict, how fatigue pools work, what recovery data means — and letting it reason from there. A coach who understands interference principles will figure out the spacing themselves. A coach following a rule will fail every time the situation doesn't match the rule exactly.
The test: if the AI needs a rule to get something right, the principle isn't strong enough yet.
Rejected: hardcoded spacing rules, threshold-based decision trees, prescribed tool call sequences.
Note (2026-03-24): The AI is still not reliably catching interference patterns (e.g. placing tempo adjacent to heavy squats). The principle may not be strong enough on its own — under active investigation.

Daily summaries as primary memory layer Decided: March 2026
The conversation history grows unboundedly. Loading all messages from all time would quickly exceed context windows and become expensive. We needed a compression mechanism.
V1 summaries were too lossy — compressing "I'm jet lagged and exhausted from travel" into generic "athlete reported fatigue." The specific context that makes coaching intelligent disappeared in compression.
We chose rich daily summaries written from the coach's perspective — specific facts with dates, the coach's interpretation and inference, not just what happened but what it means. The quality of the summary is the quality of the memory.
The summariser prompt explicitly requires specificity and inference: "Athlete said 'I just can't face the gym today' despite 81 HRV and 58 RHR — third time this month subjective fatigue has contradicted recovery metrics" is the standard, not "athlete reported fatigue."
Rejected: loading all raw messages, structured memory extraction, rolling window without summaries, separate signals table.

Context index for depth-on-demand Decided: March 2026
Loading everything on every request is expensive and noisy. But arbitrary cutoffs create blind spots.
We chose a foundation layer that always loads — last 7 summaries, athlete profile, current plan, today's data — plus a context index that describes what's available in the deeper layer. The AI reads the index and decides whether going deeper would improve the response. If yes, it retrieves via tool call.
The context index format: static description written once in the prompt describing what each data source contains and when to use it, plus a dynamic inventory generated at context build time from simple database queries — row counts and date ranges. No AI generation needed for the inventory itself.
Rejected: arbitrary time-based cutoffs, loading everything always, no depth layer.

Two context loads based on tab Decided: March 2026
The full foundation layer is appropriate for planning tabs — Today, Week, Season, Coach. But for Session tab, the athlete is mid-workout and needs fast, focused responses.
Session tab gets a lean context — brief athlete profile, today's plan, today's messages. Full depth available via tool if needed. The brain is the same, the load is optimised for the task.
Rejected: identical context load for all tabs, no context optimisation.

Observe, surface, confirm, store for profile updates Decided: March 2026
Every update to athlete profile or user preferences follows the same pattern: the AI observes a pattern, surfaces it conversationally, gets confirmation, then writes a new version. The versioning preserves history — newest row wins, older rows available if a stored inference needs to be reverted.
Rejected: silent profile updates, structured attribute fields with discrete update logic.

Meso structure — start date, end date, goal only Decided: March 2026
Minimum viable meso structure for v1 is a goal in natural language and a date range. Start date, end date, goal. That's enough for the AI to reason about where the athlete is in the block and what the current week should look like. No phase labels, no structured targets — those emerge from the coaching conversation.
This affects the schema directly — the mesocycles table needs nothing beyond these three fields plus athlete_id and timestamp.
Rejected: predefined phase categories, structured weekly targets per phase, rigid periodization templates.

System prompt and context separation at API level Decided: 2026-03-24
The brain (coaching-brain.md + tab instruction) was originally concatenated with the context block into a single system prompt string. The AI treated behavioral instructions and athlete data with equal weight, causing instructions like communication style and response length to be ignored.
We separated them: brain goes in the Anthropic API `system` parameter (system-level authority), context block goes as the first user message (information-level). The AI responds to the context with a coaching opener, then conversation flows naturally.
This was validated in the Anthropic Workbench — same brain, same context, dramatically better instruction-following when separated versus concatenated.
Also tested and rejected: two system blocks (brain as block 1, context as block 2 in the system parameter). Both blocks having system-level authority produced the same poor results as concatenation. The context must be at user level.
Rejected: single concatenated system prompt, two system blocks, context attached to every user message.

Context sent once, not on every message Decided: 2026-03-24
Early implementation attached the context block to every user message. This caused compounding duplication — the context block (including TODAY'S MESSAGES which grew each turn) was sent on every request inside the latest message, while the same conversation was also in the history array. By 12 messages deep, the full conversation existed twice in every API call.
Fixed by sending context as the first user message only. The AI's opener is the response to that context. All subsequent messages are raw conversation. Context is always in the conversation history because it's the first message, but it's never re-attached.
Rejected: context on every message, context as system blocks.

Cross-tab message filtering Decided: 2026-03-24
TODAY'S MESSAGES in the context block was duplicating the current tab's conversation — the same messages were already in the history array. Filtering TODAY'S MESSAGES to exclude the current tab eliminates duplication while preserving cross-tab awareness (messages from other tabs still appear).
Rejected: removing TODAY'S MESSAGES entirely (would lose cross-tab awareness), including all messages (duplication).

Model upgrade to Sonnet 4.6 Decided: 2026-03-24
Sonnet 4 (claude-sonnet-4-20250514) could not reliably follow communication style constraints — responses consistently too long and formatted despite explicit instructions. Sonnet 4.6 (claude-sonnet-4-6) follows the same instructions tightly. This was the single largest factor in fixing the communication style.
Tested by running identical prompts in the Workbench on 4.6 while the app ran on 4. Night and day difference.

No markdown in the brain document Decided: 2026-03-24
The brain document originally used markdown headers (## Section 1, etc). The AI reads markdown-formatted instructions and mirrors that formatting in responses — even while being told not to use headers or bold. Stripping all markdown from coaching-brain.md and using plain text section labels (SECTION 1 — IDENTITY AND ROLE) removed this trigger.
Also removed the markdown header "## YOUR CONTEXT FOR THIS SESSION" from route.ts where it bridged the brain and context block.

Pre-computed day names on all dates Decided: 2026-03-24
The AI was converting YYYY-MM-DD dates to day names incorrectly — called March 23rd (a Monday) "Sunday" because it assumed long runs happen on weekends. Rather than instructing the AI to stop guessing, we pre-compute the day name in the context builder. Every date in the context block now appears as "2026-03-23 (Monday)". The AI reads the label and uses it. No calculation, no errors.
Implemented as a formatDate() utility in context.ts applied to: today's date, summary dates, weekly plan days, mesocycle dates, readiness dates, context index ranges.

Auto-opener on Coach tab Decided: 2026-03-24
The Coach tab now automatically fires a request on component mount with no user message. The AI reads the context block and responds with a coaching opener. This aligns with the spec ("AI initiates on first open of the day") and is a natural consequence of the context-as-first-message architecture.
The opener is a real response, not a canned message. It varies based on what's in the context — recent training, recovery state, block position.

SCOPE DECISIONS
Build for one, architect for many Decided: March 2026
V1 had the athlete profile hardcoded in the prompt. Adding a second user would require a rebuild.
We chose to keep v1 focused on a single athlete but build the data model with athlete_id on every table from day one. Adding a second user is a data problem, not a rebuild. The onboarding flow is deferred to a later version.
Rejected: fully generic onboarding in v1, hardcoded athlete profile in prompt.

Deferred: structured run splits Decided: March 2026
Kilometre-by-kilometre split data deferred until Garmin/Strava integration makes automatic population viable. Rich notes on runs capture the qualitative detail in the meantime.
Rejected: splits table without integration, manual split logging.

Deferred: voice input for running Decided: March 2026
Voice is V2. Lifting session coaching demonstrates the core coaching loop first. Running session coaching via text is functional but not ideal for the live coaching vision.
Rejected: voice-first session experience in v1.

Deferred: onboarding flow Decided: March 2026
Proper onboarding deferred until there are users to onboard. Data model supports multiple athletes from day one. The onboarding conversation gets built when it's needed.
Rejected: generic onboarding in v1, form-based onboarding.

TOOL LAYER DECISIONS

Tool layer build order Decided: April 2026
Layer 1: Infrastructure (tool-use loop in route.ts) + all 12 tool definitions in lib/tools.ts — all definitions written before any executors. Layer 2: Retrieval tool executors (get_history, get_weekly_plan, get_mesocycles). Layer 3: Write tool executors (log_sets, log_run, commit_weekly_plan, commit_today_plan, update_athlete_profile, update_user_preferences, log_readiness, delete_log_entry, update_log_entry). Each tool QA'd individually.
Rejected: building tools without upfront schema definition, building write tools before retrieval.

Streaming during tool-use loops Decided: April 2026
Collect full response server-side including all tool call loops. Stream only the final text response to the frontend. Simpler than streaming partial text between tool calls, avoids frontend complexity.
Rejected: streaming text chunks between tool calls, streaming tool call status to frontend.

Executor context interface Decided: April 2026
Every tool executor receives a shared context object containing athlete_id and localDate, passed from route.ts. Uniform interface regardless of tool. localDate comes from the client, never computed server-side.

Exercise and run_type naming — open strings, no hardcoded vocabulary Decided: April 2026
No enums, no canonical list, no translation layer. Open string fields in the database. Context index enriched with distinct exercise names and distinct run_types from the athlete's data so the AI sees existing vocabulary on every request. AI uses natural language comprehension plus existing vocabulary to match names. New exercises get a clear canonical name created by the AI. End-of-session playback is the natural confirmation point for the athlete to see and correct names. No shorthand mappings stored in athlete profile — the AI reasons from context, not lookup tables.
Rejected: hardcoded exercise enum, structured vocabulary/translation layer, shorthand mapping in athlete profile.

Session logging — batch after playback, not real-time Decided: April 2026
During a live session, the AI coaches in real time but does not write to the database set-by-set. When the session is complete, the AI plays back the full session as a natural coaching reflection and logs only after the athlete has seen the playback. The AI reads language and context to recognise when a session is complete — no explicit command required. If the app crashes mid-session, conversation history is preserved in messages table and the AI offers to log on next load. Outside of live sessions (Coach tab, Today tab), completed training is logged immediately and shown to the athlete for correction.
Rejected: log-as-you-go with corrections, accumulate with explicit confirmation prompt.

Session ID on sets table — deferred Decided: April 2026
Two-a-day sessions will group as one session under the distinct-date approach. Acceptable for now. Session ID can be added later without breaking changes.

Non-today logging requires explicit date confirmation Decided: April 2026
When logging sets, runs, or readiness for any date other than today, the AI confirms the date with the athlete before calling the tool. Prevents date errors on retroactive logging.

update_log_entry field validation via information_schema Decided: April 2026
The update_log_entry executor validates that all keys in the updates object are actual columns on the target table. Column list retrieved via information_schema.columns query, cached in memory at first call. No hardcoded column lists.
Rejected: hardcoded column allowlists, unvalidated passthrough.

Weekly plan uses target_date + offset_weeks, not week_start Decided: April 2026
commit_weekly_plan and get_weekly_plan both take target_date (YYYY-MM-DD) and optional offset_weeks (integer, default 0). The executor snaps to Monday using getWeekStartMondayUtc. The AI never does date arithmetic — "this week" passes localDate with offset 0, "next week" passes localDate with offset 1, "the week of May 3rd" passes 2026-05-03 with offset 0.
Rejected: AI calculating Monday dates, hardcoded week references in context block, week_start as direct parameter.

Accept double tool call for delete/update Decided: April 2026
Deleting or updating a logged entry requires the row ID. The AI calls get_history first to find it, then calls delete_log_entry or update_log_entry. Two calls per correction. Corrections are rare, the extra round trip is invisible to the user.
Rejected: fuzzy matching in executor (fragile with duplicate sets), embedding IDs in session playback (only works for immediate corrections).

Daily summary — not a tool, background generation on first load Decided: April 2026
Daily summaries are not generated by the coaching AI mid-conversation. On first load of a new day, the context builder checks for any dates with messages but no summary. Generates summaries for the most recent 3 unsummarised dates per load — naturally handles gaps (rest days, days the app isn't opened). Timezone-correct because localDate comes from the client device. No cron job needed.
Rejected: cron job (timezone issues with multiple athletes), tool on the coaching AI (wrong context for summary generation), check-yesterday-only (misses multi-day gaps).

create_mesocycle tool added Decided: April 2026
13 tools total (3 retrieval, 10 write). create_mesocycle takes start_date, end_date, goal (natural language), and optional notes. Called after the athlete confirms the block in conversation. Goal field carries all the detail — frequency, session types, approach, intensity arc — in natural language. No structured fields for training parameters.
Rejected: structured meso fields (target_frequency, session_types, phase labels), separate from spec's natural language approach.

Tab instructions can reinforce and amplify brain principles Decided: April 2026
Tab-specific instructions are allowed to re-emphasise principles that already live in the brain when those principles are disproportionately important in that tab's context. Brevity matters everywhere but is critical on Today and Session. Time awareness matters everywhere but is most relevant on Today. Interference checking matters everywhere but is most important on Week.
This is a weighting mechanism, not duplication. The brain carries the principle. The tab instruction turns up the volume where it matters most.
Rejected: strict separation where tab instructions contain only net-new behaviour.


Session tab merged into Today
Decided: April 2026
Session was removed as a standalone tab. The daily flow — calibrate, confirm, live coach, reflect — now happens in a single conversation on Today. The transition from pre-session to live coaching is triggered by the athlete confirming the plan (commit_today_plan fires). The AI reads the conversation to know which phase it's in rather than being told by a tab switch. Bottom nav goes from five tabs to four: Today, Week, Season, Coach. Today's tab instruction covers both the old today.md and session.md content, trimmed ~30% by removing redundancies with the brain. Historical messages with tab: "session" remain in the database unchanged.

Loading screen tied to opener stream
Decided: April 2026
Loading screen previously dismissed on a fixed 2-3 second timer independent of the chat. Now dismisses when the first visible text from the opener starts streaming. Connected via a window event ("opener-started") dispatched from useChat when the first non-thinking text chunk arrives. Loading screen moved from layout.tsx to today/page.tsx — only the daily entry point needs it. If the API call fails, openerStarted fires anyway so the loading screen never hangs.
Daily summary generation runs before opener, not in parallel

Decided: April 2026
Daily summaries are the primary memory layer — the opener's context loads the last 7 summaries to understand recent history. If yesterday's summary doesn't exist when the opener fires, the AI is blind to yesterday. Summary generation must complete before the opener fires, not run in parallel. The sequence: loading screen shows → /api/summarise generates missing summaries (up to 3, excluding today) → summariesReady flips true → useChat fires opener with fresh summaries in context → loading screen dismisses on first visible text. useChat accepts an enabled parameter (default true) so other tabs are unaffected.

Sonnet over Haiku for daily summaries
Decided: April 2026
Considered Haiku for speed and cost (summaries run daily, behind a loading screen where speed matters). Chose Sonnet because the summary prompt requires inference, not just compression — connecting data to patterns, deciding what's signal vs noise, making observations about the athlete. A shallow summary doesn't just affect tomorrow, it affects every future conversation that reads it. Speed difference is ~1 second per summary, negligible behind a loading screen. Cost is one call per day, negligible in absolute terms. Optimise for quality of the memory layer, not speed.

Unique constraint on daily_summaries (athlete_id, date)
Decided: April 2026
Added a unique constraint on (athlete_id, date) in the daily_summaries table. Primary motivation: race condition where Today tab unmounts and remounts quickly, firing two /api/summarise calls simultaneously. Both check the DB, both see no summary, both generate and write. The unique constraint ensures the second write fails at the DB level. Code-level idempotency checks handle 99% of cases, the constraint handles the race condition.

Debug panel at /debug route
Decided: April 2026
Added an in-app debug panel accessible at /debug during development. Displays tool calls (name, params, result), daily summary generation (dates, output), context loaded, and errors. Built as a fully self-contained component (DebugPanel.tsx) with a global in-memory log array — no integration with ChatView, tabs, or the state architecture. Log calls are one-liners in route.ts and tool-executor.ts. To remove: delete the component, delete the import, search for debugLog and remove those lines. No structural dependencies. Chose /debug route over in-app gesture for simplicity during dev.

Per-tab summary pre-load counts
Decided: April 2026
The original "Two context loads based on tab" entry described a full-foundation load that pre-loaded the last 7 daily summaries for planning tabs. Actual behaviour is now {today: 3, week: 3, season: 0, coach: 0}. Today and Week get 3 recent summaries pre-loaded because recent history is directly relevant to planning this week. Season and Coach pre-load 0 summaries because they operate over longer horizons where the right access pattern is tool-driven get_history retrieval against whatever window the conversation calls for — pre-loading a fixed recent window would bias them toward short-horizon thinking. A richer reflective-memory layer for Season/Coach (pattern recognition across months) is on the roadmap but not yet built; until then the context index plus get_history is the interface.
Rejected: loading 7 summaries uniformly across tabs, loading zero summaries for Today/Week.

Week tab auto-opener — Wednesday onward, empty next week
Decided: April 2026
The Week tab fires an auto-opener nudging next-week planning only when dow >= 3 (Wednesday onward) AND no weekly plan exists for next week. Mon/Tue is too early to nudge about next week — the athlete is still in the current week and doesn't yet know how it's going. Once next week has a committed plan, the nudge is no longer helpful. Wednesday is the threshold because it gives the athlete enough of the current week to judge shape and fatigue before committing to next week's structure. Outside this window the Week tab opens silently with no opener.
Rejected: nudging on any day regardless of next-week state, nudging from Monday, always firing an opener on Week tab open.

Summary layer is prior-day memory, not today-state compaction
Decided: April 2026
Daily summaries are generated for yesterday and older — explicitly not today. The summariser query in getRecentSummaries uses .lt("date", localDate) and the generation route skips today. Today's state lives in three distinct context tags: <today_plan> (committed session), <readiness> (HRV/RHR/recovery/sleep), and <cross_tab_messages> (conversations from other tabs today) — plus the live message history on the current tab. Compacting today into a summary before the day is over would freeze an incomplete picture. Summaries are memory across days, not within a day.
Rejected: generating a today summary at load time, treating the last-N-summaries window as a rolling 24-hour compaction.

Streaming partial text between tool calls — supersedes "Streaming during tool-use loops" above
Decided: 2026-04-23
Multi-tool turns (common on Today when readiness-then-plan flows, and across Coach reflection) created noticeable dead air between user send and final text — the UI felt stalled. We now stream the model's text between tool calls as ephemeral live feedback, rendered as italic "thinking" on the client. Only the post-tool final text is persisted to messages. Intermediate thinking is not stored and is not part of the response contract with the athlete — it exists solely as live UX.
The split is carried on the wire by in-band null-byte delimiters (\x00THINKING\x00 and \x00FINAL\x00). The FINAL delimiter is emitted atomically with the final text via emitFinalTurn in app/api/chat/route.ts — never speculatively — so a zero-text final response from the model cannot desync the client. This fixes the \x00FINAL\x00-rendered-verbatim bug seen on 2026-04-23 after the Opus 4.6→4.7 upgrade, which surfaced a latent double-FINAL emission on the safety-net path.
Because intermediate thinking is ephemeral, substantive coaching — the read, the recommendation, the reasoning — must land in the post-tool text, not the pre-tool slot. Pre-tool scaffolding ("pulling up your recent sessions") is fine but is not a coaching slot. This is principle-constrained in prompts/chat/base.md per "Principles not rules" — the prompt tells the model *why* (what persists is what it says last), not a word-count rule.
Rejected (reaffirmed): persisting intermediate text as part of the response (conflates ephemeral scaffolding with coaching, and the model can redistribute content freely across slots so a protocol fix can't replace the prompt steer); dropping the thinking display in favour of a pure spinner (loses the live-feedback UX that prompted the original supersession).

Structured persistence for assistant turns that use tools — tried, reverted
Decided: 2026-04-23 / Reverted: 2026-04-30
Symptom: the brain double-logged a run — said it had logged, later offered to log again, wrote a second row, then when challenged claimed no prior log existed. Hypothesis at the time: messages rows stored only the final text, so on turn N+1 the model had no structured record of its own tool_use/tool_result and could not trust its own narration of "I logged it".
Tried: a nullable jsonb `blocks` column on messages, populated on assistant rows whose response went through the tool loop, holding the full Anthropic MessageParam sequence (assistant(text+tool_use), user(tool_result), …, assistant(text)). historyWithLastAssistantCached expanded blocks into apiMessages on later turns; useChat refetched blocks after each stream so same-session follow-ups carried the tool record. Cache_control stripped at storage, reapplied on rehydration.
Reverted before reaching prod (column was applied, code was uncommitted, zero rows ever written): replaying full tool_use/tool_result sequences across every subsequent turn drags large historical retrieval payloads into context every request — a real intelligence tax on Opus 4.7, which compounds long-low-novelty context into duller responses. The fix was also symptomatic: the model not trusting its own narration is the surface — the deeper problem is that today's writes aren't visible in context at all, so the model has no grounded way to know what it already did.
Direction to try next instead: (a) surface today's actual writes (sets, runs, plan changes, readiness) in the volatile context block as plain text, parallel to how cross_tab_messages and readiness already render — the model sees "logged 3x5 squat @ 100kg at 14:32" every turn without replaying tool_use blocks; (b) idempotency in the write executors themselves — log_sets/log_run/log_readiness check for an equivalent recent entry and return {logged: true, duplicate_of: …} instead of writing again, so the database stays clean even if the model ignores context.
Rejected (still): deduping in each write executor *as a stand-alone fix* (patches symptom only); persisting text-only and relying on prompt discipline ("remember you logged it"); storing the full API sequence as separate messages rows (complicates display and summariser).

REFLECTION LAYER DECISIONS
(Session of 2026-04-22. Originally a separate addendum file; merged here 2026-10-04.)

Reflection layer — separate brain, Coach tab only
Decided: April 2026
Until this build, the app had no dedicated mechanism for surfacing longitudinal insights. The coaching brain only reasoned within a live conversation — it never proactively looked across weeks to flag things the athlete hadn't noticed.
We built a reflection layer that runs on Coach first-open-of-day. It replaces the Coach opener with two insight cards (pulse and deep) generated by a dedicated reflection pass.
The reflection brain is separate from the coaching brain. Different job (find one meaningful pattern and surface it) vs (coach this conversation), different context, different tool access. The "one central brain for coaching" principle still holds — reflection is its own brain, not a tab lens.
Coach only, not Today. Today is the high-frequency tab and needs to stay fast; reflection takes 30-50s combined on first open. Coach already had debug-terminal framing and no workflow overhead, making it the natural home.
Rejected: reflection as a tab instruction on Coach (wrong — it's a distinct job, not a framing), reflection running on every tab (would slow Today, unnecessary on Week/Season), one brain with a "reflection mode" parameter (conflating two different jobs).

Two passes, two prompts — pulse and deep
Decided: April 2026
Pulse runs over the last seven days (tactical, fresh). Deep runs over full history (longitudinal, behavioural). They surface different kinds of insight — sharing a prompt with a window parameter would have pulled the short-horizon thinking into the long, or vice versa.
Both share the same bar — an insight is worth surfacing if it impacts coaching, is informative for the athlete, and they probably haven't noticed. Both use the same 1-10 significance scale. Investigation methods differ: pulse reads summaries as primary source; deep uses summaries for orientation only and investigates raw tables via get_history.
Rejected: single brain with a window parameter, single brain with conditional instructions per pass length, deep as a cron-triggered weekly pass (premature optimisation for single-athlete build).

Reflection context is purpose-built, not reused from chat
Decided: April 2026
Reflection's inputs are genuinely different from chat's — no today's messages, no weekly plan, no cross-tab messages. Instead: profile, preferences, prior insights of the matching type, summaries sized to the pass, and (for deep) the context index so it knows what's available via get_history.
Built as buildPulseContext and buildDeepContext in lib/reflection-context.ts, separate from buildContext in lib/context.ts. Shares formatDate and getContextIndexCounts helpers but assembles its own block. Chose this over a reused buildContext with a new tab value because the conditional branches would have outweighed the duplication.
Pulse context: profile + prefs + last 3 pulse insights + last 7 summaries. ~1,500 tokens.
Deep context: profile + prefs + last 5 deep insights + last 7 summaries + context index. ~1,700 tokens.
Pulse gets no deep insights; deep gets no pulse insights. Each pass builds on its own prior outputs.
Rejected: extending buildContext with a reflect tab, reusing chat context wholesale, sharing prior insights across pass types.

log_insight as the output mechanism
Decided: April 2026
The reflection pass outputs its insight via a log_insight tool call rather than returning prose. Matches the write-tool pattern used elsewhere in the app (update_athlete_profile, commit_today_plan, create_mesocycle). The tool call IS the output — no final text streamed to client.
log_insight is not in HOT_TOOLS for any chat tab. It lives in the tools registry but only /api/reflect includes it in its tool set. Chat routes have no access. Symmetric to how reflection tools don't bleed into chat.
Rejected: structured JSON response parsed post-hoc, free-form prose with regex extraction, model writing directly to the table via raw SQL.

Reflection runs inline on Coach first-open-of-day, parallel dispatch
Decided: April 2026 (superseded 2026-10-04 — see "Reflections moved to the background" below)
Pulse and deep fire in parallel on Coach mount. Wall time is max(pulse, deep) ≈ 30-35s rather than sum ≈ 50s. They don't share data — deep doesn't read pulse's output — so sequential offered no value.
Idempotency enforced server-side via unique constraint on (athlete_id, date, type). Second open of Coach on the same day returns cached rows directly as JSON without running the loop.
Coach opener removed entirely. No generic "hey how's it going" fallback — the reflection cards are the content. If the athlete ignores the cards and types freely, chat proceeds normally.
Rejected: sequential pulse-then-deep (wasted latency), background cron (couldn't ship fast, adds scheduling complexity for single-athlete build), opener as fallback when reflection fails (reduces product clarity).

Significance score visible in UI from day one
Decided: April 2026
Both insights render with a significance score (1-10) visible as a badge. Always surface the top candidate regardless of score — a 3 surfaces the same way a 9 does, just with a different number visible. Debug signal: we see what the model calls a 3, a 5, an 8, and can tune the bar later.
Known limitation: early self-grading is compressed at the top of the scale. Every insight from the first two runs landed 7-8 regardless of quality. Model under-discriminates at the top. To be tuned once enough insights accrue to calibrate against.
Rejected: hiding scores below a threshold (breaks debug loop), dropping scores entirely (no calibration signal), visual severity treatment (premature polish).

Streaming intermediate reasoning from reflection route
Decided: April 2026
Reflection route streams model reasoning and tool-call announcements to the client using the same \x00THINKING\x00 / \x00FINAL\x00 delimiter protocol as /api/chat. The athlete sees the model thinking and investigating before the insight lands — kills perceived latency on a 30-50s process.
FINAL payload is JSON, not prose — contains the inserted insight row plus iterations count. Client parses and populates the card.
Rejected: pure JSON response with spinner (30s blank spinner is unacceptable UX), streaming the final prose (there is no final prose — the tool call IS the output), server-sent events (no value over the existing delimiter protocol that the rest of the app uses).

2026-10-04 — PERFORMANCE, WEARABLES, BACKGROUND WORK

Extended thinking on Week, Season, Coach and reflection — not Today
Decided: 2026-10-04
Extended thinking is enabled on /api/chat for week, season and coach (budget 2048 tokens) and on every /api/reflect call (budget 4096). Today stays off: it is the high-frequency tab, its opener gates the loading screen, and the latency cost of thinking would be paid on every turn there. Week and Season are planning tabs where calendar arithmetic and interference reasoning benefit from a scratchpad; Coach is low-frequency; reflection is an investigation loop where thinking before each tool call is the point.
Thinking is decided once per request and applied to every call in that request's tool loop — never toggled mid-loop, so thinking blocks in earlier assistant turns stay valid for later calls. Thinking deltas are never streamed to the client and never persisted; the in-band THINKING/FINAL delimiter protocol is unchanged and carries only text. cache_usage entries log thinking_enabled; SDK 0.80.0 counts thinking tokens inside output_tokens.
Rejected: thinking on every tab (Today latency), toggling thinking per call based on whether tools were used (invalidates earlier turns), surfacing thinking text in the UI (the pre-tool text slot already serves as live feedback).

Per-tab tool iteration caps, parallel tool execution
Decided: 2026-10-04
MAX_TOOL_ITERATIONS on chat is per tab: today 5, week 5, season 10, coach 10. Reflection: pulse 8, deep 20 (raised from 15 the same day — see the guard entry). Today and Week are conversational and should resolve in a few calls; Season and Coach do multi-step retrieval over long horizons and were hitting the old single cap of 5 mid-investigation. Within one turn, all tool_use blocks now execute in parallel (Promise.all, results mapped back in block order) in both the chat and reflect loops.
Known cost of parallel execution: ordering inside a turn is no longer guaranteed, so a delete_log_entry and an update_log_entry for the same id emitted in one turn can race. Accepted — corrections are rare and the model is told to get_history first.
Rejected: one global cap, raising the cap uniformly (lets Today wander), sequential tool execution (added latency on every multi-tool turn).

Deep reflection loop guard — commit with two calls left
Decided: 2026-10-04
The deep pass was running out of iterations without calling log_insight: it kept investigating and never committed. Rather than a hard "you must call log_insight by iteration N" rule, the loop appends one message when exactly two calls remain and no insight has been logged — "Two rounds left. Call log_insight now with the best insight you've verified so far." — as a trailing text block on the tool-results user turn, and logs guard_fired. The model still decides what to say; the guard only names the deadline. Typical deep pass is ~100–155s; worst observed spans approached the 300s Vercel Hobby cap, so maxDuration=300 is exported from reflect, chat and summarise, and guard_fired frequency is the signal to watch.
Rejected: forcing log_insight via tool_choice on the last call (yields unverified insights), lowering max_tokens, accepting no_insight_logged as a normal outcome.

Context index via a single get_context_index RPC — amends "Per-tab summary pre-load counts"
Decided: 2026-10-04
Timing instrumentation (a "timing" debug entry per chat request: context_ms, first_token_ms, per-round api/tool ms, tool_rounds, total_ms) showed the context build as a fixed cost on every turn. getContextIndexCounts was 13 queries per request — three count/min/max, two bare counts, and two distinct-vocabulary scans over sets and runs that grew with every session. Replaced with one Postgres function, get_context_index(p_athlete_id) returning jsonb in the same shape as ContextIndexCounts (supabase/migrations/20261004000000_create_get_context_index_rpc.sql). In the same pass: cross-tab messages filtered server-side instead of in JS; the insights loader skipped off the Coach tab; Coach now pre-loads 7 daily summaries (the April entry set it to 0 — this matches the pulse pass's seven-day window so follow-up chat on the cards shares it); Anthropic model ids centralised in lib/models.ts.
Rejected: caching the index in-process (stale across Vercel instances), dropping the vocabulary lists (the open-strings naming decision depends on them), a materialised view (write-side complexity for a read that is already one cheap query).

Whoop as an automatic readiness source — OAuth, strict no-overwrite merge
Decided: 2026-10-04
Readiness was manual-only via log_readiness. Whoop v2 is now a source. OAuth: /api/whoop/connect → /api/whoop/callback with cookie-based state; tokens in wearable_tokens with RLS enabled and no policies, so only the server's service-role client can read them, never the browser's anon key. getValidToken refreshes and persists Whoop's rotated refresh tokens. Mapping: recovery_score, hrv_rmssd_milli (one decimal), resting_heart_rate, sleep hours as light + slow-wave + REM (what the Whoop app calls time asleep). Wake date is sleep.end shifted by Whoop's own timezone_offset — correct across travel and DST — with athletes.timezone (new column, default Europe/London) only as a fallback. readiness.source = 'whoop' marks provenance; manual rows stay null.
Merge rule is strict no-overwrite: if any readiness row exists for the date, manual or Whoop, Whoop does not write. The athlete's own log always wins, and a re-synced recovery never silently changes a number the coach has already reasoned from. A partial unique index on (athlete_id, date) where source='whoop' makes concurrent syncs safe, after two overlapping backfill runs double-inserted 15 dates. Sync never trusts Whoop's collection ordering (it sorts by created_at itself — observed ordering contradicted the documented newest-first) and refuses wake dates more than 2 days old, so it can never write ancient rows.
Rejected: upsert/overwrite of manual rows (the coach may already have reasoned from them), field-by-field merge (ambiguous provenance), storing tokens in an app table with RLS off (the anon key would read them), trusting documented ordering.

Sync on open rather than a webhook for readiness, initially — superseded the same day
Decided: 2026-10-04 (morning) / Superseded: 2026-10-04 (see the morning-trigger entry below)
First cut: Today fires POST /api/whoop/sync on mount, fire-and-forget, never gating the opener; the readiness realtime subscription picks up the insert when it lands. Chosen to ship the data source in one session for one athlete without a public endpoint, signature verification, or background execution. Backfill is a separate secret-gated GET for history.
Superseded once sync was stable: the webhook became the morning trigger for far more than readiness. Sync-on-open remains as the safety net.
Rejected at the time: webhook-first (more surface area before the mapping was proven), cron polling (no wake signal, timezone guesswork).

Whoop's recovery webhook as the morning trigger, with a run-claim table
Decided: 2026-10-04
Three expensive things ran when the athlete opened the app each morning: Whoop sync (fast), yesterday's summary (gates the Today opener), and the Coach reflections (pulse + deep, 100–155s). Whoop scoring the recovery is the "they woke up" signal, wherever the athlete is in the world. POST /api/whoop/webhook verifies Whoop's v2 signature (base64 HMAC-SHA256 of timestamp + raw body, keyed with the app client secret — Whoop issues no separate webhook secret; headers X-WHOOP-Signature and X-WHOOP-Signature-Timestamp), returns 200 immediately, and continues via waitUntil from @vercel/functions (Next 14.2 has no after()). Only recovery.updated is acted on; its id is the sleep UUID, resolved exactly via sleep → cycle_id → that cycle's recovery.
lib/morning.ts then runs: readiness for the wake date; yesterday's summary if missing; pulse and deep for the wake date if missing, in parallel. Each step is idempotent by date, logged as a morning_chain debug entry, and continues on failure. The wake date comes only from Whoop's offset — there is no athlete-timezone "today" gate; the existing 2-day staleness guard is what stops an old recovery regenerating past summaries or insights. summarise, reflect and sync were pulled out of their routes into lib functions so the chain calls them directly; the routes are thin wrappers with unchanged responses.
Duplicates: Whoop may deliver several events for one recovery and deliveries can overlap. morning_chain_runs (PK athlete_id + wake_date; status running/done/error; claim_token rotated on reclaim) makes the expensive steps run once per date; a run stuck "running" for 6 minutes is reclaimable. The unique indexes on readiness, daily_summaries and insights remain the DB-level backstop, and log_insight treats a duplicate-key hit as "already logged" so a Coach fallback racing the chain ends cleanly instead of looping.
Rejected: cron (no wake signal, timezone guesswork), sleep.updated as an additional trigger (recovery.updated always follows; it only added duplicates), gating on today-in-athlete-timezone (a second clock — Whoop's offset is the only one), unique indexes alone without a claim (two overlapping chains would both spend ~150s of Opus before one insert failed), a 5-minute replay window (Whoop retries over about an hour and the docs don't say retries are re-signed; replaying an idempotent chain is harmless — tolerance is 2 hours).

Today's opener stays live — not pre-generated
Decided: 2026-10-04
The morning chain never generates or touches chat messages: not the Today opener, not Coach. The opener is cheap and should react to the moment — time of day, what the athlete has already said on other tabs, readiness that may have landed minutes earlier. Pre-generating it at wake time would freeze a read before the athlete has done anything, and a pre-written assistant row in messages would hydrate as history and suppress the live opener. What the chain does is make the opener's inputs ready: yesterday's summary and today's readiness exist before the app opens, so /api/summarise on mount is a no-op and the loading screen is short.
Rejected: pre-generating the opener in the background, writing any assistant message from a background job, pre-building and caching the context block (cheap to build live, stale within minutes).

Reflections moved to the background — supersedes "Reflection runs inline on Coach first-open-of-day, parallel dispatch"
Decided: 2026-10-04
Pulse and deep now run inside the morning chain, after yesterday's summary is written and in parallel with each other. Coach opens to cached cards. The April decision to run them inline on first open was explicitly a ship-fast choice ("background cron couldn't ship fast"); the webhook removes the scheduling problem a cron would have had — no timezone guesswork, no fixed hour, the trigger is the athlete waking. Parallel dispatch is retained (they share no data). The on-mount fallback on Coach remains: if the chain hasn't run or failed, Coach generates as before. No Sonnet fallback, unchanged.
Resolves the open question "Cron / background generation of reflections — worth it?" from the reflection-layer open list.
Rejected: a daily cron (timezone, no wake signal), running reflections before the summary (they read it), generating a Coach opener from the insights (the cards are the content, unchanged).

Persist all model text; NDJSON stream protocol; thinking on Today; code-generated tool status lines — supersedes "Streaming partial text between tool calls" and amends "Extended thinking on Week, Season, Coach and reflection — not Today"
Decided: 2026-10-05
The chat route persisted only the text of the final tool-free round. When the model began its answer before a tool call, that opening was shown and then discarded, so saved replies started mid-thought — and the client history, cross_tab_messages and the summariser all read the truncated version. This was the open diagnostic "pre-tool text snapping at the FINAL_DELIMITER"; option (b) is taken, with the prompt moved to match.
Every round's text is now the reply and is persisted: each round's text is trimmed and non-empty rounds are joined with a blank line. All rounds — initial, tool rounds and the safety net — go through one streaming runRound() in app/api/chat/route.ts, so every round streams; the model-fallback wrapper, cache_control placement, per-request thinking config and the assistant-turn push are unchanged. The safety-net call sets tool_choice none, so it can only answer.
The in-band \x00THINKING\x00 / \x00FINAL\x00 delimiters are replaced on /api/chat by NDJSON (application/x-ndjson), one JSON object per line: {"t":"text","v"} for reply text from every round as it streams, {"t":"status","v"} for one code-generated line per tool_use block, {"t":"done"} at the end of the turn. The server trims each round as it streams (leading whitespace dropped, trailing whitespace held back), so the client's concatenation of text frames equals the persisted row exactly. useChat parses line-buffered NDJSON; ChatView keeps the partial reply visible and shows the status line in the dimmed slot. /api/reflect and the Coach cards keep the delimiter protocol.
Status lines come from lib/tool-status.ts (describeToolCall: "pulling up your runs…", "checking this week's plan…", default "working…"), never from the model. base.md Section 5 now says everything written in text is kept, reasoning belongs in thinking, and nothing is written alongside a tool call; week.md's sequence check is done in thinking.
Thinking is on for every tab: Today 1024 tokens, Week/Season/Coach 2048. With all text persisted, thinking is the only place reasoning can go, so Today needs it too; the smaller budget limits the latency cost on the high-frequency tab. The timing debug entry records text_chars per round.
Rejected: keeping intermediate text ephemeral and tightening the prompt alone (the model redistributes content across slots; the protocol made any pre-tool coaching disappear), persisting only pre-tool plus final text (arbitrary cut for multi-round turns), model-written status text (it is coaching-voice text that must then be either kept or discarded — the original problem), server-sent events (no gain over NDJSON on a fetch stream), leaving Today without thinking (reasoning would leak into the persisted reply).

The route now drops blank history entries and the hook drops an empty placeholder. A turn that ends with no reply text streams a fixed line ("Lost my thread there — send that again?") and logs the stop reason; nothing is persisted. Decided: 2026-10-05.
