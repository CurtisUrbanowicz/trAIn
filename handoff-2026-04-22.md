State of the App — 2026-04-22

A code-first walk of what actually exists in this repo. Where spec and code disagree, the code wins and the drift is called out.

Note on prior handoff: there is no `handoff-2026-04-16.md` in the working tree or git history. This document is structured to match the section order requested (Tabs, Brain, Context, Tools, Database, API routes, Known gaps, Surprises).


TABS

`app/page.tsx` — single-line server redirect to `/today`.

`app/layout.tsx` — root layout. Loads Inter, renders `<BottomNav />` globally. `LoadingScreen` is NOT in here; it was moved to `app/today/page.tsx` per the April 2026 decision to tie dismissal to the opener stream.

`app/components/BottomNav.tsx` — four tabs, hard-coded: Today, Week, Season, Coach. `/debug` is not in the nav and there is no link to it from anywhere in the UI — it is reached by typing the URL directly.

Today (`app/today/page.tsx`)
- `ATHLETE_ID` constant `bc1c4cd0-a69a-4317-9b46-f7072d3bd886` hard-coded at top of every client component (today, week, season, LoadingScreen, useChat). Same UUID five places.
- On mount: fetches the newest `plans` row for today (`session_type`, `exercises`, `notes`). Exercises are tolerated as string array, object array, or JSON string (see `app/today/page.tsx:40-45`).
- Realtime: subscribes to `plans` INSERTs filtered by `athlete_id`; any insert refetches.
- Runs `POST /api/summarise` on mount, flipping `summariesReady` in `.finally()` regardless of success/failure.
- Listens for a `window` event `opener-started` to flip `ready`, which dismisses `LoadingScreen`.
- Renders `<LoadingScreen ready={ready} />` plus `<ChatView tab="today" enabled={summariesReady}>` with a small "today plan" card as sticky child. If `plan.exercises` is an empty array, the card section still renders but without the exercises subtree.
- `enabled={summariesReady}` is what gates the auto-opener; the chat hook only fires once summaries have run.

Week (`app/week/page.tsx`)
- On mount: fetches current-Monday and next-Monday `weekly_plans` in parallel, plus `runs` and `sets` across the two-week window for green completion checkmarks.
- Realtime: subscribes to `weekly_plans` INSERTs; any insert refetches both weeks.
- "This week" accordion auto-expands when a plan exists (`app/week/page.tsx:120`). "Next week" stays collapsed.
- Nudge auto-opener: `shouldNudge = dow >= 3 && nextWeekPlan == null` — Thursday onward, when next week has no committed plan, the chat fires an opener automatically. Otherwise Week is silent on open.
- Passes `<ChatView tab="week" autoOpen={shouldNudge}>`.

Season (`app/season/page.tsx`)
- On mount: fetches the active mesocycle (`lte start_date today, gte end_date today`, newest by timestamp), plus 52 weeks of `sets` and `runs`.
- No realtime subscription.
- Derived views (`useMemo`): meso progress % and week-of/total; two-month calendar with activity shading; per-exercise top-set line chart with 4/12/52w toggle; per-week running volume bar chart with same toggle.
- Renders `<ChatView tab="season">` — `autoOpen` defaults to `true`, so Season fires an opener on first-of-day load.

Coach (`app/coach/page.tsx`)
- Five lines. Just `<ChatView tab="coach" />`. `autoOpen` defaults to `true`.
- No data fetching, no realtime, no sticky children — chat fills the tab.

Debug (`app/debug/page.tsx`)
- Not in `BottomNav`. Reached at `/debug` only.
- Polls `GET /api/debug/log` every 2 seconds. Color codes: `tool_call` and `tool_result` purple, `context_loaded` grey, `summary_generated` green, `error` red. No colors defined for `summary_gap_filled`, `cache_usage`, or `model_used`, which render in the default muted color.
- "Clear" button POSTs `{ action: "clear" }`.

ChatView (`app/components/ChatView.tsx`)
- Thin wrapper around `useChat(tab, enabled, autoOpen)`. Handles message list, thinking bubble, input bar, auto-scroll, Enter-to-send.
- Skips rendering empty assistant placeholders while `thinking` is non-null.

useChat (`lib/useChat.ts`)
- On mount (gated by `enabled`): queries `messages` for today+tab. If any rows exist, hydrates history and skips the opener. Filters out messages with empty `content`.
- If no messages and `autoOpen === false`, flips `openerStarted`, fires the `opener-started` event, and stops — meaning Week before Thursday never auto-fires even on first load.
- If no messages and `autoOpen === true`, POSTs `/api/chat` with an empty `message` string. This is the opener.
- Stream decoding handles three states based on in-band delimiters: raw text → message, `\x00THINKING\x00` → thinking bubble, `\x00FINAL\x00` → final message. Edge case at `lib/useChat.ts:93-105`: if THINKING arrived but FINAL never did, strips the delimiter and treats remainder as final text.
- Dispatches `window` event `opener-started` on first visible text chunk (via `isOpenerStream` ref), which is what the Today `LoadingScreen` listens for.

Routes that exist but aren't in the bottom nav: `/debug`, `/api/*`.


THE BRAIN

`coaching-brain.md` (6.9 KB) — five sections, plain text (no markdown headers, per the Decision Log strip). Labelled `SECTION 1 — IDENTITY AND ROLE` through `SECTION 5 — TOOLS`:
1. IDENTITY AND ROLE — who the coach is, evidence-based mandate, life context.
2. HOW TO THINK AND ACT — investigate before advising, hypothesis model, time as input, observe/surface/confirm/store, profile discipline.
3. CONVERSATION STATES — four states (CHECKING IN, PLANNING, EXECUTING, REFLECTING) with focus/tools/depth/format per state.
4. HOW TO COMMUNICATE — texting tone, no bullets/headers/preamble, lead with recommendation.
5. TOOLS — thoroughness default, write-to-keep-record-current, "write a brief natural message first then call", days_between invariant, explicit mention that tools are discoverable via search.

`tab-instructions/today.md` — opener states (training / rest / no plan / same-day reopen), pre-session and mid-session length caps (1-2 sentences / even shorter), commit_today_plan as the state switch into live coaching, playback-then-log rule, soft-confirmation list ("kk", "let's go", "heading out").

`tab-instructions/week.md` — frames Week as the "tetris problem," two entry points (no plan vs plan exists), instructs day-names-not-ISO in output ("Monday April 7"), forbids meso creation on Week ("surface the case for Season tab, don't nag"), mid-week-adjustments-are-live.

`tab-instructions/season.md` — zoom-out, data-first, longitudinal insight bar, six meso-planning intake questions, time horizon athlete-led, five phase-transition tones.

`tab-instructions/coach.md` — read across full history before responding, debug-terminal framing, first-load intake flow for a missing athlete profile (under 200 words, v1 captures goals / injuries / baselines / tendencies / patterns).

Together: one brain + one tab instruction, concatenated into the system prompt string via `loadSystemPrompt`.


CONTEXT BUILDER

`lib/context.ts` — server-only (uses `fs/promises`).

`buildContext(athleteId, tab, localDate, localTime?) -> { systemPrompt, contextBlock }` loads nine things in parallel via `Promise.allSettled`:
1. `loadSystemPrompt(tab, localDate)` — reads `coaching-brain.md` + `tab-instructions/${tab}.md`, concatenates with `\n`, caches in a module-level `Map<TabType, {value, cachedDate}>`. Cache is invalidated when `localDate` changes, so new day = one fresh filesystem read per tab per process lifetime.
2. `getAthleteProfile` — newest `athlete_profile.content`.
3. `getUserPreferences` — newest `user_preferences.content`.
4. `getActiveMesocycle` — newest `mesocycles` row where `start_date <= localDate <= end_date`. `mesocycles.name` is in the DB but not read.
5. `getCurrentWeeklyPlan` — newest `weekly_plans.days` for this Monday.
6. `getTodaysReadiness` — newest `readiness` row for today.
7. `getTodaysMessages` — all `messages` rows for today across all tabs.
8. `getRecentSummaries(limit)` — newest N `daily_summaries` rows where `date < localDate`. Limit driven by `SUMMARY_LIMIT[tab]` — see divergence below.
9. `getContextIndexCounts` — per-table counts + earliest/latest dates for `daily_summaries`, `runs`, `sets`; counts for `mesocycles` and `weekly_plans`; distinct `sets.exercise` and `runs.run_type` vocabulary lists.

Context block structure (XML-style tags, joined by `\n\n`):
```
<context_instructions>
<date>
<week_dates>      — current and next Monday, pre-computed with day name
<athlete_profile>
<user_preferences>
<mesocycle>       — or "No active mesocycle"
<weekly_plan>     — 7 day lines with formatted dates, or "No plan committed this week"
<readiness>       — four named fields, "none" for missing
<daily_summaries count="N">  — or "None pre-loaded. Use get_history..."
<cross_tab_messages>  — filtered to exclude current tab per Mar 24 decision
<context_index>   — seven lines of counts / ranges / vocabularies
```

`formatDate(yyyy-mm-dd)` attaches the UTC day name: `"2026-04-22 (Wednesday)"`. Used on every date in the context block.

System prompt assembly and cache — `loadSystemPrompt` produces `${brain}\n${tabInstructions}` and caches in-process keyed by (tab, localDate). This is the cache used by `systemPromptCache` in `lib/context.ts:64`. Separately, the Anthropic API call in `app/api/chat/route.ts:188,264,339` wraps the prompt in `{ type: "text", text, cache_control: { type: "ephemeral", ttl: "1h" } }` so the provider side also caches it.

Divergence from "Two context loads based on tab" (Decision Log, March 2026, Section 4.2 of Overall Scope):

- Spec says Full foundation tabs (Today, Week, Season, Coach) get "last 7 daily summaries — always." Code (`lib/context.ts:36-41`):
  - today: 3
  - week: 3
  - season: 0
  - coach: 0
  No tab loads 7. Season and Coach load zero daily summaries pre-loaded; both tab instructions tell the AI to retrieve via tool before advising, which is the apparent rationale, but this is not logged as a decision.
- Spec distinguishes "Session tab — lean context." There is no session tab anymore (removed April 2026). The lean/full split has been replaced de facto with a 3/0 split on the remaining four tabs.
- "Today's plan" is NOT loaded into the context block. `plans` is not queried in `buildContext`. The AI infers today's plan from `<cross_tab_messages>` and the Today card shown to the user separately.


TOOLS

`lib/tools.ts` defines 14 tools. Grouped as in the brain:

Retrieval
- `get_history(table, date_from?, date_to?, exercise?, run_type?, limit=20)` — tables: `sets | runs | daily_summaries | readiness`. For `sets`, `limit` counts distinct dates (all sets on each date are returned); for the others, `limit` counts rows.
- `get_weekly_plan(week_start)` — week_start must be a Monday; executor rejects non-Mondays with a suggested correction.
- `get_mesocycles()` — all mesocycles newest first.

Write (logging)
- `log_sets(sets[], date?)` — duplicate-suppresses on (athlete_id, date, exercise, weight_kg, reps), inserts non-dupes, then returns the full session for the date.
- `log_run(distance_km, run_type, duration_min?, avg_pace?, avg_hr?, notes?, date?)` — no duplicate check on the executor side; tool description delegates it to the AI ("check via get_history first").
- `log_readiness(hrv?, rhr?, recovery_score?, sleep_hours?, date?)` — all optional.

Write (planning)
- `commit_today_plan(session_type, notes?, exercises?)` — always writes today's date. Hard-codes `type: "today_plan"`.
- `commit_weekly_plan(week_start, days)` — Monday-check as with `get_weekly_plan`. All seven day keys required in schema.
- `create_mesocycle(start_date, end_date, goal, notes?)` — plain insert.

Write (athlete model)
- `update_athlete_profile(content)` — inserts a new version row.
- `update_user_preferences(content)` — inserts a new version row.

Corrections
- `delete_log_entry(table, id)` — table restricted to `sets | runs`. Fetches row to verify athlete ownership before deleting; returns a human description of what was deleted.
- `update_log_entry(table, id, updates)` — table restricted to `sets | runs`. Rejects `athlete_id`, `id`, `timestamp` keys. Everything else is passed through to Supabase.

Utility
- `days_between(date_from, date_to)` — returns `"N days"`. Absolute value, so direction is lost.

Hot vs deferred per tab (`HOT_TOOLS` in `lib/tools.ts:374`):
- today: `get_history, log_sets, log_run, commit_today_plan`
- week: `get_history, commit_weekly_plan, get_weekly_plan, days_between`
- season: `get_history, get_mesocycles, create_mesocycle, days_between`
- coach: `get_history` only

Non-hot tools are tagged `defer_loading: true`. A `tool_search_tool_regex_20251119` tool is prepended to the list on every request so the model can fetch deferred schemas by regex when it needs them. The last hot tool in the list gets `cache_control: { type: "ephemeral", ttl: "1h" }` so the tool block caches with the system prompt.

Tool-use loop in `app/api/chat/route.ts`:
- `MAX_TOOL_ITERATIONS = 5`.
- Initial call is `anthropic.messages.stream({...})` — text deltas are piped directly to the client as bytes. A `content_block_start` of type `tool_use` flips `hasToolUse = true`.
- If no tool_use at all, the streamed text IS the final response and is persisted to `messages`.
- If there is tool_use, the route emits `\x00THINKING\x00` to the client, appends the assistant turn to `apiMessages`, executes every `tool_use` block via `safeExecuteTool`, then appends a user turn of tool_result blocks.
- Loop continues with `anthropic.messages.create` (non-streaming) for iterations 1..4. On an iteration with no `tool_use`, emits `\x00FINAL\x00` and streams text via `controller.enqueue`, then breaks.
- "Safety net" at `app/api/chat/route.ts:331-352`: if the loop exhausts and `fullResponse` is still empty, one more `create` call is made and its text is sent as the final.
- Only the final coaching text is saved to the DB; intermediate text between tool calls streams to the client (visible) but does not persist.

Model selection and fallback (`app/api/chat/route.ts:113-160`):
- Type: `"claude-opus-4-7" | "claude-sonnet-4-6"`.
- First call tries Opus 4.7; on an error whose message contains `"overloaded"` (case-insensitive), waits 2 seconds and tries Opus 4.7 once more. If that also overloads, switches `currentModel` to Sonnet 4.6 for the rest of the request.
- `firstCallComplete` gates this logic — the fallback decision is made on the first call only. Every subsequent tool-loop call reuses whatever model the first call settled on. No mid-loop model switching.

API ROUTES

`POST /api/chat` (`app/api/chat/route.ts`)
- Accepts JSON: `{ message: string, localDate: string (YYYY-MM-DD, required), localTime?: string, tab?: "coach"|"today"|"week"|"season", history?: { role, content }[] }`. Unknown or missing tab silently falls back to `"coach"`.
- Builds context, pushes `context_loaded` debug entry, persists the user message to `messages` immediately (not awaiting the AI response — except the insert is awaited inside a `try/catch`, so a DB failure logs but doesn't fail the request).
- When `message === ""`, no user history is appended — only the context block acts as the opener prompt.
- Streams via the response body with the delimiter protocol described above. Model Opus 4.7 primary, Sonnet 4.6 fallback.

`POST /api/summarise` (`app/api/summarise/route.ts`)
- Accepts `{ athleteId, localDate }`.
- Phase 1: finds dates with messages but no `daily_summaries`, excluding today, takes the most recent 3. For each, re-checks idempotency, fetches `messages`, `runs`, `sets` for the date, builds a single user content string with sections `MESSAGES:`, `RUNS:`, `SETS:` (the latter two are raw JSON dumps), calls Anthropic, writes the summary.
- Phase 2 (gap-fill): for this Monday and previous Monday, reads the latest `weekly_plans.days`; for any day <= yesterday with no summary, no messages, no runs, no sets and a non-empty `session_type`, synthesises a short stub — `"Rest day — planned."` or `"Planned ${sessionType} — no activity logged."` — and inserts as the day's summary. This branch never calls an LLM.
- Model for phase 1: `claude-opus-4-7`. The Decision Log ("Sonnet over Haiku for daily summaries") pre-dates this; recent commits `bc9ed34 → e526bc8 → f128f30` show the summariser moved to Sonnet 4.6, was reverted to Opus 4.6, then upgraded to Opus 4.7 alongside chat. None of these three post-April-16 model changes are in the Decision Log.
- `max_tokens: 500`. System prompt embedded inline in the route, not in `coaching-brain.md`.

`GET /api/debug/log` — returns newest 200 `debug_log` rows.

`POST /api/debug/log` — `{ action: "clear" }` hard-deletes all `debug_log` rows (`.gte("id", 0)`).

`GET /api/debug/context?tab=&localDate=` (`app/api/debug/context/route.ts`)
- Returns `{ tab, localDate, weekStart, systemPromptLength, contextBlockLength, systemPrompt, contextBlock }` for inspection.
- No client UI links to this; it is a URL-only tool.

SURPRISES

Where the code diverges from `Decision_Log.txt` / `Overall_Scope.txt` and the drift is not itself logged as a decision. File paths and line numbers below refer to the as-committed state on `main` at this snapshot.

1. Daily-summary pre-load counts diverge from both the spec's "last 7 always" and any logged per-tab split.
   - `lib/context.ts:36-41` — `{ today: 3, week: 3, season: 0, coach: 0 }`.
   - Spec § 4.2 says 7 always for the four planning tabs. Decision Log "Two context loads based on tab" distinguishes planning vs session, not today/week vs season/coach. Season and Coach tab instructions both tell the AI to retrieve history before advising, so the lean pre-load is arguably intentional — but that reasoning is nowhere in the Decision Log.

2. `update_log_entry` does not validate fields against `information_schema`.
   - Decision Log April 2026: "The update_log_entry executor validates that all keys in the updates object are actual columns on the target table. Column list retrieved via information_schema.columns query, cached in memory at first call."
   - Actual `lib/tool-executor.ts:412,422-424`: only blocks a hardcoded `NON_UPDATABLE = Set("athlete_id", "id", "timestamp")`. Any other key, including typos and columns that don't exist on the table, gets passed straight to Supabase — which will surface a DB error but only after a round trip.

3. `commit_weekly_plan` / `get_weekly_plan` use `week_start` directly, not `target_date + offset_weeks`.
   - Decision Log April 2026: "commit_weekly_plan and get_weekly_plan both take target_date (YYYY-MM-DD) and optional offset_weeks (integer, default 0). The executor snaps to Monday using getWeekStartMondayUtc. The AI never does date arithmetic."
   - Actual schemas: `lib/tools.ts:63-70, 174-202` — single required `week_start` parameter. Executors `lib/tool-executor.ts:228-233, 556-561` validate that `week_start` IS a Monday and reject otherwise, which pushes the Monday-computation burden back onto the model. Two pre-computed Mondays are published in the context block under `<week_dates>` (`lib/context.ts:366-370`) so the model can copy them verbatim — this is how the model avoids arithmetic. It is a different solution than the Decision Log describes and is not itself logged.

4. Debug log is a persisted Postgres table, not in-memory.
   - Decision Log April 2026 ("Debug panel at /debug route"): "Built as a fully self-contained component with a global in-memory log array — no integration with ChatView, tabs, or the state architecture."
   - Actual `lib/debugLog.ts:19-30` writes every `pushLog` to `public.debug_log` via Supabase. `getLog` reads the 200 newest rows. Currently 1,148 rows in that table.
   - Knock-on: clearing via `POST /api/debug/log { action: "clear" }` runs `delete().gte("id", 0)` (`lib/debugLog.ts:52`) which relies on the `id` column being numeric — but the column is a UUID. That comparison semantically means "id >= 0" against UUID text and may behave unexpectedly at scale.

5. Daily-summary model is Opus 4.7, not Sonnet.
   - Decision Log April 2026 explicitly titled "Sonnet over Haiku for daily summaries."
   - Actual `app/api/summarise/route.ts:150` — `model: "claude-opus-4-7"`. Commits `bc9ed34` → `e526bc8` → `f128f30` show the route went Sonnet 4.6 → Opus 4.6 → Opus 4.7 after the decision was logged. The decision was quietly reversed.

6. Model fallback chain in chat route is not in the Decision Log.
   - `app/api/chat/route.ts:113-160` — Opus 4.7 primary, retry once after 2s on `overloaded`, then Sonnet 4.6 for the remainder of the request. Fallback decided on the first call only; subsequent tool-loop iterations reuse `currentModel`. This entire mechanism was introduced around the Opus 4.7 upgrade (`f128f30`) without a logged decision.

7. Tool search / deferred tools mechanism is not in the Decision Log.
   - `lib/tools.ts:381-403` prepends `{ type: "tool_search_tool_regex_20251119", name: "tool_search_tool_regex" }` to every request and tags non-hot tools with `defer_loading: true`. The coaching brain references this behaviour at `coaching-brain.md:75, 83`: "Some tools are loaded immediately, others are discoverable via search. If you need a tool that isn't currently visible, search for it." No Decision Log entry names this tool, the deferred-loading split, or the per-tab hot set.

8. `mesocycles.name` column drift.
   - Schema has `name TEXT NULLABLE`. Spec § 3.2 lists only `id, athlete_id, start_date, end_date, goal, notes, timestamp`. `create_mesocycle` does not write it. `getActiveMesocycle` in `lib/context.ts:119-145` does not read it. Vestigial.

9. Today's planned session is never loaded into the context block.
   - Overall Scope § 4.2 lists "Current weekly plan — full structure" and "Today's readiness" but the April 2026 Today-tab decision describes commit_today_plan firing as the state switch to live coaching. Despite this, `buildContext` does not query `plans` — the AI only learns today's committed session from `<cross_tab_messages>` or from tool calls. The Today `plan` card shown to the user is fetched directly by the client, not surfaced into the AI's context. Not logged as a decision either way.

10. `tool_result` debug entry type is defined but never emitted.
    - `lib/debugLog.ts:3-11` declares `"tool_result"` in `DebugEntryType`. No `pushLog("tool_result", …)` exists anywhere in the repo. The debug UI has a color entry for it (`app/debug/page.tsx:13`) but the type is unreachable. Tool call results are bundled into the `tool_call` entry itself (`lib/tool-executor.ts:651-656`), truncated at 200 chars.

11. `getRecentSummaries` uses `<` not `<=`, and there is no code path that would make today's summary appear in the context even if it somehow got generated.
    - `lib/context.ts:221` — `.lt("date", localDate)`. The summariser route also explicitly excludes today (`app/api/summarise/route.ts:46`). Consistent design, but worth calling out: the opener never sees a summary for "today" — the context instead relies on `<readiness>`, `<cross_tab_messages>`, and live messages.

12. Week-tab auto-opener is gated on `dow >= 3 && nextWeek == null`.
    - `app/week/page.tsx:122-123`. Not in the spec or Decision Log. Effectively: Week is silent Mon-Wed and silent any time next week's plan exists. No corresponding prompt in `tab-instructions/week.md` explaining what the nudge opener should say.

13. Season and Coach auto-openers use `autoOpen=true` default.
    - `app/season/page.tsx:239` and `app/coach/page.tsx:4` both invoke `<ChatView tab=…>` without `autoOpen`. Given `ChatView`'s default (`ChatView.tsx:14`), these fire on every first-of-day load — consistent with Coach spec but not explicitly logged for Season.

14. `useChat` opener hydration skips the auto-opener whenever any persisted message for today+tab exists (`lib/useChat.ts:129-142`).
    - Implication: reopening Today mid-day after a morning conversation means no fresh opener, even if the user would expect one after a new training session was logged elsewhere. This matches "Same-day reopen — conversation persists, no new opener" in `tab-instructions/today.md`, but the same rule applies unconditionally to all four tabs.

15. Cross-tab messages include historical `session` tab rows.
    - `app/api/chat/route.ts:14-19` and `app/api/debug/context/route.ts:10-15` both restrict `TAB_VALUES` to `coach, today, week, season`. But `getTodaysMessages` in `lib/context.ts:191-208` pulls all rows regardless of tab, and the filter in `formatContext` (`lib/context.ts:442`) is `m.tab !== tab` — so a `session`-tagged message from earlier today (if it existed) would appear in `<cross_tab_messages>` on all four tabs. No rows with `tab='session'` exist today, but nothing prevents future ones if a client with the old tab string is still calling the route.

16. `days_between` loses sign.
    - `lib/tool-executor.ts:604` — `Math.abs(...)`. A call with `date_from` later than `date_to` returns the magnitude but not the direction. Brain tells the AI to use this tool to verify time gaps before stating them, so in practice callers order the dates deliberately; still, the tool result alone cannot disambiguate direction.

17. `LoadingScreen` writes `localStorage.lastOpenDate` on every dismiss, even when the screen was never shown.
    - `app/components/LoadingScreen.tsx:30-34`. If `lastOpen === todayStr()` the component returns early and never sets state to `"visible"`; if `ready` flips while still hidden, the effect at `:103-105` only calls `dismiss` when `state === "visible"`, so the state write is guarded. This one is fine in practice but the control flow is intricate enough to be worth flagging on read.

18. Gap-fill summary branch commits zero-LLM stub summaries.
    - `app/api/summarise/route.ts:224-283`. If a day was planned, has no messages, no runs, no sets, no existing summary, and isn't `rest`, it writes `"Planned ${sessionType} — no activity logged."` as the day's summary. Future reads of that day via `get_history(daily_summaries)` will return this stub. This is not in the Decision Log.

19. `parseTab` silently coerces unknown/undefined tab to `"coach"`.
    - `app/api/chat/route.ts:21-25` and `app/api/debug/context/route.ts:25-31`. No 400 is returned. An old client calling with `tab: "session"` would transparently get the Coach brain with Coach tool hotness.

20. `commit_today_plan` ignores any `date` input — it's hard-coded to `context.localDate`.
    - `lib/tool-executor.ts:580` (`date: context.localDate`). The tool's own description says "This only writes for today's date," which matches, but the schema exposes no `date` parameter at all — so the AI can't even attempt a retroactive today-plan commit. `log_sets`, `log_run`, and `log_readiness` all allow a `date` override; `commit_today_plan` alone does not.
