TABS

Routing is Next.js App Router. `app/page.tsx` is a single-line redirect to `/today`. `app/layout.tsx` loads two fonts via `next/font/google` — Inter (default `--font-inter`) and Source Serif 4 at weights 400/500 (`--font-serif`) — exposes both variables on `<html>`, and renders `<BottomNav />` globally. `LoadingScreen` is mounted only inside `app/today/page.tsx`.

`app/components/BottomNav.tsx` has four tabs hard-coded — Today, Week, Season, Coach — rendered with `lucide-react` icons (`Sun`, `Calendar`, `TrendingUp`, `MessageCircle`). `/debug` is not in the nav; reach it by URL.

`ATHLETE_ID` = `bc1c4cd0-a69a-4317-9b46-f7072d3bd886` is hard-coded in every client component that needs it (`today`, `week`, `season`, `LoadingScreen`, `useChat`), plus the API routes. Single-athlete build, per the "Build for one, architect for many" decision.

Today (`app/today/page.tsx`)
- On mount: parallel fetches of newest `plans` row (`session_type`, `exercises`, `notes`) and newest `readiness` row (`recovery_score`, `hrv`, `rhr`, `sleep_hours`) for today.
- Realtime: subscribes to `plans` and `readiness` INSERTs filtered by `athlete_id`. Any insert refetches.
- Runs `POST /api/summarise` on mount, flips `summariesReady` in `.finally()` regardless of success/failure. The opener is gated on `summariesReady`.
- Listens for a `window` event `opener-started` to flip `ready`, which dismisses `LoadingScreen`.
- Layout: `<LoadingScreen ready={ready} />` plus `<ChatView tab="today" enabled={summariesReady}>` with `<ReadinessHero readiness={readiness} date={getLocalDate()} />` and `<PlanCard plan={plan} />` as sticky children above the chat thread.
- Visual pass shipped today: readiness "hero" (date label + orb + HRV/RHR/Sleep column) and plan card (accent-bordered surface, title in Source Serif, bullet list of exercises). The orb ring colour ramps grey→green on a score 0–100 via `oklch(${0.5 + pct*0.25} ${pct*0.14} 150)`.

Week (`app/week/page.tsx`)
- On mount: parallel fetches of current-Monday and next-Monday `weekly_plans` (newest row per `week_start`) plus `runs` and `sets` across the two-week window for the green check icon on completed days.
- Realtime: subscribes to `weekly_plans` INSERTs; any insert refetches both weeks.
- This-week accordion auto-expands when a plan exists. Next week stays collapsed until clicked.
- Auto-opener: fires only when `dow >= 3` (Wednesday onward) AND no `weekly_plans` row exists for next Monday. Otherwise `<ChatView tab="week" autoOpen={shouldNudge}>` with `shouldNudge = false` means Week opens silently. This gate is logged as "Week tab auto-opener — Wednesday onward, empty next week" (April 2026).
- Monday math uses local-time `Date` with the Sun-shift-back trick in `getMonday`. Matches `isoMonday` in Season but differs from `getWeekStartMondayUtc` in `lib/context.ts` which is UTC-based. For Europe/Central timezones the two agree; for far-west-of-UTC timezones they can disagree by a day — not exercised today but worth naming.

Season (`app/season/page.tsx`)
- On mount: fetches the active mesocycle (`mesocycles` newest where `start_date <= today <= end_date`, selecting `start_date, end_date, goal, name`) plus 52 weeks of `sets` and `runs`.
- Realtime: subscribes to `mesocycles` INSERTs and refetches the active meso on change.
- Derived views (`useMemo`): meso progress (week-of / total, percent, clamped); two-month calendar (prev + current) with activity shading from the union of sets+runs dates; lifting line chart with 4w/12w/52w toggle and per-exercise buttons; weekly running volume bar chart with same time-range toggle.
- `<ChatView tab="season" autoOpen={false}>` — Season does not auto-fire an opener. Prior handoff claimed Season inherited Coach's autoOpen=true default; that is no longer true on current `main`.
- Meso card: shows `meso.name` when present, otherwise falls back to `"${formatMesoDate(start)} – ${formatMesoDate(end)}"`. Progress bar uses `--accent`.

Coach (`app/coach/page.tsx`)

For missing type(s), POSTs to `/api/reflect` in parallel with streaming body reading. Decodes the `\x00THINKING\x00` / `\x00FINAL\x00` delimiter protocol from `/api/reflect` (chat moved to NDJSON on 2026-10-05; reflect did not).

Other emitted types — `summary_gap_filled`, `cache_usage`, `model_used` — render with the default muted color. `tool_result` is in the map but is never emitted by any code path (see KNOWN GAPS).

ChatView (`app/components/ChatView.tsx`)
- Thin wrapper around `useChat(tab, enabled, autoOpen)`. Manages message list, status line, input bar, auto-scroll, Enter-to-send.
- Coach/assistant bubbles render in Source Serif; athlete/user bubbles render in Inter. Different paddings, border radii, and bubble colors for each. User bubble gets a subtle indigo border (`--border-athlete-bubble`). Pill-shaped input; send button is always mounted but only solidifies to indigo once input has text (prevents layout shift).
- The last streaming assistant message renders at 70% opacity until complete, and stays visible while a status line shows.
- Empty assistant placeholders are skipped. The tool status line (`status` from useChat) renders in a dimmed italic bubble below the messages.

useChat (`lib/useChat.ts`)
- On mount (gated by `enabled`, default true): queries `messages` for today+tab. If any rows exist, hydrates as history, skips the opener, fires `opener-started`. Empty-content rows are filtered out of history display.
- If no rows and `autoOpen === false` (Season, Week-before-Wed, Week-with-plan): flips `openerStarted`, fires `opener-started`, stops — no API call.
- If no rows and `autoOpen === true` (Today, Coach, Week-from-Wed-with-no-next-plan): POSTs `/api/chat` with an empty `message`. The context block is the opener prompt.
- Stream decoding is line-buffered NDJSON (since 2026-10-05): `{"t":"text","v"}` appends to the last assistant message, `{"t":"status","v"}` sets `status`, `{"t":"done"}` or stream end clears it. Text also clears the status. The bubble text equals the persisted `messages` row.
- Dispatches `window` event `opener-started` once, on the first text frame (tracked by `isOpenerStream` ref). `LoadingScreen` listens for it.
- Same-day reopen: because hydration skips the opener whenever any persisted message exists, reopening any tab mid-day shows the prior conversation without re-firing the opener. Matches `tab-instructions/today.md`; applies unconditionally to all four tabs.

LoadingScreen (`app/components/LoadingScreen.tsx`)
- Shown only on first open of the day, gated on `localStorage.lastOpenDate === today ? hidden : visible`.
- 300 ms after mount, sets a fallback subtitle ("Catching up on your training…"), then upgrades based on Supabase lookups: if the most recent sets/runs date is yesterday, "Catching up on yesterday's session…"; if ≥ 3 days ago, "Been a few days…"; else tries the active meso and shows `"Week N of your block…"`.
- Dismisses when parent flips `ready`. Fade-out 300 ms. `localStorage.lastOpenDate` is set inside `dismiss()`, which is only called when the screen was actually visible.
- Renders `tr[ai]n` with the middle two letters in `--accent`.


THE BRAIN

`coaching-brain.md` (83 lines, plain text — no markdown headers, per the March 2026 "No markdown in the brain document" decision). Five sections:
1. IDENTITY AND ROLE — evidence-based mandate, life context is coaching context.
2. HOW TO THINK AND ACT — investigate before advising, hypothesis model, time as input, observe-surface-confirm-store, profile discipline ("the profile is not a journal"), honesty.
3. CONVERSATION STATES — CHECKING IN, PLANNING, EXECUTING, REFLECTING, with focus/tools/depth/format per state.
4. HOW TO COMMUNICATE — texting tone, no bullets/headers/preamble, lead with recommendation.
5. TOOLS — thoroughness default, write-to-keep-record-current, "write a brief natural message first, then call", `days_between` invariant ("never state a number of days, weeks, or time gap without calling"), discoverable-via-search note.

Tab instructions in `tab-instructions/{today,week,season,coach}.md`:
- `today.md` — opener framing by time-of-day, calibration (validate good feelings with data; protect when data says otherwise), soft-confirmation list ("kk", "let's go", "heading out", "will start at 6"), `commit_today_plan` as the state switch into live coaching, playback-then-log rule.
- `week.md` — "tetris problem" framing, two entry points (no plan vs plan exists), day-names-not-ISO in output, no meso creation (surface the case for Season, don't nag), mid-week adjustments are live.
- `season.md` — data-first, longitudinal insight bar, meso-intake questions, time horizon athlete-led, five phase-transition tones. Explicit four-field requirement for `create_mesocycle`: Name (propose yourself, ≤ 4 words), Goal, Structure, optional Notes.
- `coach.md` — first-open-of-day insight bar, intake flow when no athlete profile exists, debug-terminal framing. Gained a TODAY'S INSIGHTS section: insights are visible to the athlete as cards and to the brain in `<todays_insights>`; refer to them naturally, don't re-explain them, don't force the topic if the athlete ignores them.

Two additional prompts in the same directory for the reflection layer: `pulse-brain.md` and `deep-brain.md`. These are full system prompts on their own, not concatenated with `coaching-brain.md` and not wrapped with a tab instruction. Loaded by `lib/reflection-context.ts`, not by `loadSystemPrompt` in `lib/context.ts`. See REFLECTION LAYER.

System-prompt assembly (`loadSystemPrompt`): `${brain}\n${tabInstructions}`. Cached in-process per (tab, localDate) in a module-level Map — one filesystem read per tab per day per Node process lifetime. On every Anthropic API call the prompt is wrapped in `{ type: "text", text, cache_control: { type: "ephemeral", ttl: "1h" } }` so the provider also caches it.


REFLECTION LAYER

New in April 2026 (merged here from the 2026-04-22 addendum). Proactive longitudinal intelligence — replaces Coach's opener with two streaming insight cards, one for this week (pulse) and one across the athlete's full history (deep).

How it runs
- On Coach first-open-of-day, `app/coach/page.tsx` queries `insights` for today's pulse and deep rows. For whichever type(s) are missing, it POSTs to `/api/reflect` in parallel (one call per type). Cached rows render immediately; missing ones stream in.
- Reflection routes don't write to `messages`, don't participate in chat history, and don't interact with the coaching brain. They run as isolated agent loops, write one row to `insights`, and return. Coach's chat input is independent — `<ChatView tab="coach" autoOpen={false}>`, no opener.

The brain
- Two prompts alongside `coaching-brain.md`: `pulse-brain.md` (7-day reflection — ground in profile + prefs, find one meaningful pattern, verify against data, call `log_insight` with type `pulse`) and `deep-brain.md` (full-history reflection — same bar, longer horizon, expects 5–15 tool calls, verifies against raw tables).
- Both share an identical bar (impacts coaching, informative for the athlete, they haven't noticed) and a 1–10 significance scale. Categories of insight overlap (physiological, behavioural, ratios/comparisons); pulse adds "this week's horizon" framing, deep adds "multi-source joins, long horizons" as investigation guidance. Coaching-interaction patterns are explicitly NOT listed — removed after the first test run showed both passes self-auditing.
- Each reflection brain is a full system prompt on its own — not concatenated with `coaching-brain.md`, not wrapped with a tab instruction. It replaces, not extends.

Context (`lib/reflection-context.ts`, server-only)
- `buildPulseContext(athleteId, localDate)` and `buildDeepContext(athleteId, localDate)`, both returning `{ systemPrompt, contextBlock }`. Prompts cached in a module-level Map. Each does its own parallel loads via `Promise.allSettled`.
- Pulse: athlete profile (newest), user preferences (newest), last 3 pulse insights by `created_at` desc as `<prior_pulse_insights>`, last 7 daily summaries where `date < localDate` as `<recent_summaries>`.
- Deep: profile, preferences, last 5 deep insights as `<prior_deep_insights>`, last 7 summaries, and the context index (reusing `getContextIndexCounts`) as `<context_index>`.
- Both lead with `<context_instructions>`, then `<date>`, then profile/prefs/insights/summaries. Same XML-tag pattern as the main context builder. `formatDate` and `getContextIndexCounts` are exported from `lib/context.ts` for reuse.
- Pulse does not see prior deep insights; deep does not see prior pulse insights. Each pass builds on its own prior outputs.

Route (`app/api/reflect/route.ts`) — `POST { athleteId, localDate, type: "pulse" | "deep" }`
1. Validate inputs — 400 JSON on bad input before the stream starts.
2. Idempotency — query `insights` for (athleteId, localDate, type). If found, return `{ insight, cached: true }` as plain JSON. No Anthropic call, no stream.
3. Build context via `buildPulseContext` or `buildDeepContext`. Log `context_loaded` with `tab="reflect-{type}"`.
4. Start streaming. `Content-Type: text/plain; charset=utf-8`, `Cache-Control: no-store`.
5. Agent loop. Max iterations: pulse 8, deep 15. Tool set: `get_history` + `log_insight` (filtered from `lib/tools.ts` by name); `cache_control` ephemeral 1h on the last tool in the block.
6. Model `claude-opus-4-7`. On an overload error (case-insensitive "overloaded" substring), wait 2s and retry the same call once. No Sonnet fallback — diverges from the chat route. Rationale: a missed insight is acceptable, a Sonnet-quality insight erodes trust in the memory layer.
7. Text deltas stream as the model thinks, wrapped in `\x00THINKING\x00`. On each `tool_use` block, emit a synthetic announcement line (`→ {tool}({summary})`) and execute via the shared executor.
8. When `log_insight` fires successfully, set `insightLogged=true`. After the loop, query the inserted row, emit `\x00FINAL\x00` followed by `JSON.stringify({ insight, iterations, cached: false })`, close the stream.
9. If the loop hits max iterations without `log_insight`: emit `{ error: "no_insight_logged", iterations }`, log an error debug entry, close.
10. If Anthropic throws mid-stream: emit `{ error: message }` and close.
- Uses the shared `executeTool` from `lib/tool-executor.ts` with context `{ athleteId, localDate }`. Debug entries: `context_loaded` at start, `model_used` once, `tool_call` per execution (name + inputs + result, each truncated to 200 chars), `cache_usage` once at the end from the final iteration's usage, `error` on any failure path.

Tools — `log_insight` added to `lib/tools.ts`; see TOOLS.

Database — new table `insights`; see DATABASE.

Context injection for Coach follow-up chat
- `lib/context.ts` gains `getTodaysInsights(athleteId, localDate)`, returning today's pulse and deep rows if present, as an 11th parallel task in `buildContext`. Rendered as `<todays_insights count="N">` between `<daily_summaries>` and `<cross_tab_messages>`; included only when `tab === "coach"`, skipped entirely on Today, Week, Season.
- `coach.md` gained a TODAY'S INSIGHTS section (see THE BRAIN).

Coach tab UI — see TABS → Coach.

Key changes: headline-led (one-line version of the day up front); missed or modified sessions called out with the same weight as completed ones; routine table data (sets/weights/RIR, splits/pace/HR, readiness numbers) skipped unless it's the story; "Your read on the athlete" rather than generic "your read"; the load-bearing line "The summary is about the athlete, not about how you coach them."; word budget 80 (down from 100) with explicit permission to exceed when the day warrants; athlete profile prepended to the summariser input as an ATHLETE PROFILE section so summaries use correct pronouns and grounding.

CONTEXT BUILDER

`lib/context.ts` — server-only (uses `fs/promises`). Exports `buildContext(athleteId, tab, localDate, localTime?)` returning `{ systemPrompt, contextBlock }`.

Parallel loads via `Promise.allSettled` (eleven tasks):
1. `loadSystemPrompt(tab, localDate)` — brain + tab instruction, cached.
2. `getAthleteProfile` — newest `athlete_profile.content`.
3. `getUserPreferences` — newest `user_preferences.content`.
4. `getActiveMesocycle` — newest `mesocycles` row where `start_date <= localDate <= end_date`, selecting `start_date, end_date, name, goal, structure, notes`.
5. `getCurrentWeeklyPlan` — newest `weekly_plans.days` for this Monday.
6. `getTodaysPlan` — newest `plans` row for today (`session_type, notes, exercises`). Normalises `exercises` from string-array, object-array, or JSON-string into a plain `string[]`.
7. `getTodaysReadiness` — newest `readiness` row for today (four metrics).
8. `getTodaysMessages` — all `messages` rows for today across all tabs.
9. `getRecentSummaries(limit)` — newest N `daily_summaries` rows where `date < localDate`. `limit` driven by `SUMMARY_LIMIT[tab]`.
10. `getContextIndexCounts` — per-table counts + earliest/latest dates for `daily_summaries`, `runs`, `sets`; counts for `mesocycles` and `weekly_plans`; distinct `sets.exercise` and `runs.run_type` vocabulary lists.
11. `getTodaysInsights` — newest `insights` rows for (athlete_id, localDate), both types. Selects `id, type, content, significance`. Ordered pulse first, deep second.

Each loader's failure is caught and logged to console; `buildContext` substitutes safe defaults (empty strings, null, empty arrays, zero counts) and returns a valid context regardless.

Context block structure (XML-style tags, joined by `\n\n`):

```
<context_instructions>
<date>                 — YYYY-MM-DD (Weekday) with optional HH:MM local time suffix
<week_dates>           — current and next Monday pre-computed with day names
<athlete_profile>
<user_preferences>
<mesocycle>            — Name / Goal / Structure / Notes / Dates, or "No active mesocycle"
<weekly_plan>          — seven day lines with formatted dates, or "No plan committed this week"
<today_plan>           — Session / Exercises bullets / optional Notes, or "No plan committed for today."
<readiness>            — four named fields, "none" for missing
<daily_summaries count="N">  — or "None pre-loaded. Use get_history to retrieve when needed."
<todays_insights count="N">  — Coach tab only. Today's pulse + deep insights with significance scores, or "None yet today."
<cross_tab_messages>   — filtered via `m.tab !== tab` per the March 2026 cross-tab decision
<context_index>        — seven lines of counts / ranges / vocabularies
```

Reflection layer has its own context builder: `lib/reflection-context.ts`, separate from `lib/context.ts`. Shares `formatDate` and `getContextIndexCounts` as exported helpers. Does not reuse `buildContext`.

`SUMMARY_LIMIT`: `{ today: 3, week: 3, season: 0, coach: 0 }`. Logged in April 2026 "Per-tab summary pre-load counts" — planning tabs get a short recent window; Season and Coach pre-load zero and reach deeper via `get_history` on demand.

`formatDate(yyyy-mm-dd)` attaches the UTC day name to every date in the context block (e.g. `2026-04-22 (Wednesday)`). `localDate` comes from the client; the UTC day-name attachment assumes client local day ≈ UTC day for day-name purposes, which holds for the current single-athlete timezone.

`<cross_tab_messages>` includes any rows with `m.tab !== current_tab`, so historical `tab = 'session'` rows from before Session was merged into Today would surface on all four tabs if any existed today. No rows with `tab='session'` currently exist for today — `messages.tab` has five distinct values historically (`coach`, `season`, `session`, `today`, `week`), but the API layer no longer accepts `session` on write.


TOOLS

`lib/tools.ts` defines 15 tools (14 chat tools plus `log_insight`, reflection-only). Per-request, `getToolsForTab(tab)` prepends `{ type: "tool_search_tool_regex_20251119", name: "tool_search_tool_regex" }` and tags non-hot tools with `defer_loading: true`. The last non-deferred tool gets `cache_control: { type: "ephemeral", ttl: "1h" }` so the tool block participates in the same 1h cache window as the system prompt.

Retrieval (3)
- `get_history(table, date_from?, date_to?, exercise?, run_type?, limit=20)` — tables: `sets | runs | daily_summaries | readiness`. For `sets`, `limit` counts distinct dates (all sets on each date are returned). For the others, `limit` counts rows. All queries scoped by `athlete_id`.
- `get_weekly_plan(week_start)` — `week_start` must be a Monday. Executor compares against `getWeekStartMondayUtc(week_start)` and rejects with `"week_start must be a Monday. Did you mean ${computedMonday}?"` if not. The two pre-computed Mondays are published in the context block under `<week_dates>` so the model can copy them verbatim.
- `get_mesocycles()` — all mesocycles for the athlete, ordered by `start_date` desc. Selects `start_date, end_date, name, goal, structure, notes`.

Write — logging
- `log_sets(sets[], date?)` — duplicate-suppresses on `(athlete_id, date, exercise, weight_kg, reps)`, inserts non-dupes, then returns the full session for the date.
- `log_run(distance_km, run_type, duration_min?, avg_pace?, avg_hr?, notes?, date?)` — no duplicate check in the executor. Tool description tells the AI to `get_history` first.
- `log_readiness(hrv?, rhr?, recovery_score?, sleep_hours?, date?)` — all fields optional. `recovery_score` has a 0–100 range check in the executor (added today), returning `"recovery_score must be between 0 and 100"` on violation. The tool description calls `recovery_score` "a composite readiness score provided by the athlete's wearable (Oura, Whoop, Garmin); user-reported, not computed; do not infer or estimate if absent."

Write — planning
- `commit_today_plan(session_type, notes?, exercises?)` — always writes today's date (the executor hardcodes `date: context.localDate` and the schema does not expose a `date` param). Inserts a new row with `type: "today_plan"`; newest-wins. If a user wants to retroactively commit a past day's today-plan, this tool cannot do it; `log_sets`, `log_run`, `log_readiness` all expose an optional `date` override.
- `commit_weekly_plan(week_start, days)` — same Monday-check as `get_weekly_plan`. All seven day keys required in schema.
- `create_mesocycle(start_date, end_date, name, goal, structure, notes?)` — schema requires `name`, `goal`, and `structure` in addition to the date range. Executor writes all of them. The `name` and `structure` columns aren't in Overall Scope Section 3's original `mesocycles` shape; see DATABASE.

Write — athlete model
- `update_athlete_profile(content)` — inserts a new version row. Description reinforces concision (under 200 words) and observe-surface-confirm discipline.
- `update_user_preferences(content)` — same, under 150 words.

Corrections
- `delete_log_entry(table, id)` — table restricted to `sets | runs`. Fetches the row to verify athlete ownership before deleting; returns a human description of what was deleted.
- `update_log_entry(table, id, updates)` — table restricted to `sets | runs`. Blocks keys in `NON_UPDATABLE = Set("athlete_id", "id", "timestamp")`. No other key-validation. The Decision Log entry "update_log_entry field validation via information_schema" (April 2026) describes a richer validator that was never implemented; everything outside the blocklist is passed straight to Supabase, surfacing errors only after a DB round trip. Worth a call if the richer validator is still wanted.

Utility
- `days_between(date_from, date_to)` — returns `"N days"`. `Math.abs`, so direction is lost. Callers order dates deliberately.

Reflection-only
- `log_insight(type, content, significance)` — writes one row to `insights` with `status='unsurfaced'`, `surfaced_at=null`, `date=context.localDate`; returns a confirmation string with the inserted id. Not in `HOT_TOOLS` for any chat tab — only `/api/reflect` includes it in its tool set, so chat routes never see it. Schema enforces `type ∈ {pulse, deep}` and `significance ∈ [1, 10]`.

Hot tools by tab (`HOT_TOOLS` in `lib/tools.ts`):
- today: `get_history, log_sets, log_run, commit_today_plan`
- week: `get_history, commit_weekly_plan, get_weekly_plan, days_between`
- season: `get_history, get_mesocycles, create_mesocycle, days_between`
- coach: `get_history` only

Non-hot tools are `defer_loading: true` and discovered by the model via `tool_search_tool_regex`. This mechanism is described at `coaching-brain.md:75, 83`; no Decision Log entry names the tool-search tool or the per-tab hot set, but the mechanism is documented in the brain.

Tool-use loop in `app/api/chat/route.ts`:
- `MAX_TOOL_ITERATIONS` per tab (today 5, week 5, season 10, coach 10). Updated 2026-10-05.
- Every round, including the safety net, goes through one `runRound()` that calls `anthropic.messages.stream(...)`, so every round streams. The response is NDJSON (`application/x-ndjson`): `{"t":"text","v"}` for reply text deltas, `{"t":"status","v"}` for one line per `tool_use` block from `describeToolCall` in `lib/tool-status.ts` (emitted when the block's input is complete), and `{"t":"done"}` at the end.
- A round with `tool_use` blocks pushes its content to `apiMessages`, executes the tools in parallel via `safeExecuteTool`, and appends a user turn of tool results. A round with none ends the loop.
- Safety net: if the loop hits its cap or the last round wrote no text, one more round runs with `tool_choice: {type: "none"}`.
- All model text is the reply and is saved: each round's text is trimmed and non-empty rounds are joined with a blank line. The route trims as it streams, so the client's bubble equals the persisted row.
- Extended thinking is on for every tab (today 1024 tokens, others 2048). Thinking is never streamed or persisted.
- User messages are persisted immediately on receipt (awaited in a `try/catch`, so a DB failure logs but does not fail the request). Assistant messages are persisted once the stream completes.

Model selection:
- Primary: `claude-opus-4-7`. On an `overloaded` error (case-insensitive substring match), waits 2 s and retries Opus 4.7 once. If that also overloads, switches to `claude-sonnet-4-6` for the remainder of the request. `firstCallComplete` gates this — every subsequent call in the tool loop reuses whatever model the first call settled on. Not mid-loop switchable.
- Logged in the Decision Log entry "Model upgrade to Opus 4.7 with Sonnet 4.6 fallback chain." Rationale: optimise for instruction-following and judgment quality.

API ROUTES

`POST /api/chat` (`app/api/chat/route.ts`)
- Accepts JSON `{ message: string, localDate: string, localTime?: string, tab?: "coach"|"today"|"week"|"season", history?: { role, content }[] }`. Unknown/missing `tab` silently falls back to `"coach"` via `parseTab`. No 400 returned for bad tabs.
- Validates `message` is a string and `localDate` is a non-empty string. Throws on either failure (returns 500 via outer catch).
- Builds context, pushes `context_loaded` debug entry, persists the user message to `messages` (awaited, errors logged but do not fail the request).
- When `message === ""`, the API messages array is just `[{ role: "user", content: contextBlock }]` — no history, no user message. This is the opener path.
- Otherwise: `[{ role: "user", content: contextBlock }, ...history, { role: "user", content: message }]`.
- Streaming + tool loop + model fallback as described under TOOLS.
- `cache_usage` debug entry emitted after the initial stream completes with `input_tokens`, `cache_write`, `cache_read` from `stream.finalMessage().usage`.

`POST /api/summarise` (`app/api/summarise/route.ts`)
- Accepts `{ athleteId, localDate }`. Returns `{ generated: N }`.
- Phase 1: dates with messages but no `daily_summaries`, excluding today, newest-3. For each: idempotency re-check, fetch `messages + runs + sets`, build a user content string with `MESSAGES:` / `RUNS:` / `SETS:` sections (latter two raw JSON), call Anthropic, insert the summary.
- Phase 2 (gap-fill): for this Monday and previous Monday, reads latest `weekly_plans.days`. For any `day <= yesterday` with no summary, no messages, no runs, no sets, and a non-empty `session_type`, synthesises a stub — `"Rest day — planned."` or `"Planned ${sessionType} — no activity logged."` — and inserts. This branch never calls an LLM. Logs via `summary_gap_filled` debug entries.
- Model: `claude-opus-4-7`. `max_tokens: 500`. System prompt inline in the route (sharpened in commit `1831342` — emphasises preserving the athlete's own words, connecting to recent days, and density of facts/quotes over readability; ~100 word target). Rewritten again later the same day to be athlete-first — see REFLECTION LAYER → Summariser changes.

`POST /api/reflect` (`app/api/reflect/route.ts`)
- Accepts JSON `{ athleteId: string, localDate: string, type: "pulse" | "deep" }`. 400 on bad input.
- Idempotency check — returns the existing insight as plain JSON with `cached: true` if one exists for (athleteId, localDate, type).
- Builds context via `lib/reflection-context.ts`.
- Streams `\x00THINKING\x00` during the agent loop, emits synthetic `→ tool_name(summary)` lines on each tool call, then `\x00FINAL\x00` + `JSON.stringify({ insight, iterations, cached: false })` on a successful `log_insight`.
- Max iterations: pulse 8, deep 15.
- Model: `claude-opus-4-7`. 2s retry on overload, no Sonnet fallback.
- Debug entries: `context_loaded`, `model_used`, `tool_call` (per tool), `cache_usage`, `error` (on failure).

`GET /api/debug/log` — newest 200 `debug_log` rows.
`POST /api/debug/log` with `{ action: "clear" }` — `.delete().not("id", "is", null)` (fixed today; the previous `.gte("id", 0)` was semantically incorrect against UUID ids).
`GET /api/debug/context?tab=&localDate=` — returns `{ tab, localDate, weekStart, systemPromptLength, contextBlockLength, systemPrompt, contextBlock }` for inspection. No client UI links to it; URL-only tool.

They render in the default muted color, so they're technically distinguishable from other muted entries only by the `type:` label on each card — not broken, just incomplete.
