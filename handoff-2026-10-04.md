Morning chain (`8e28983`)
- `POST /api/whoop/webhook`. Verifies Whoop's v2 signature: `X-WHOOP-Signature` = base64(HMAC-SHA256(`X-WHOOP-Signature-Timestamp` + raw body, `WHOOP_CLIENT_SECRET`)), timestamp tolerance 2 hours, 401 on failure. Returns 200 immediately; the chain continues via `waitUntil` from `@vercel/functions` (Next 14.2 has no `after()`). Only `recovery.updated` is acted on; its `id` is the sleep UUID, resolved `GET /v2/activity/sleep/{id}` → `cycle_id` → `GET /v2/cycle/{cycle_id}/recovery`. `maxDuration = 300`.
- `lib/morning.ts` `runMorningChain(athleteId, sleepId, traceId)`: (1) readiness for the wake date via `syncReadiness`, (2) yesterday's summary via `summariseMissing(wakeDate)` if none exists for wake date minus one, (3) pulse and deep for the wake date via `runReflection` if missing, in parallel. Each step idempotent by date, logged as `morning_chain` `{ step, date, outcome, ms, … }`, continues on failure. The wake date comes only from Whoop's offset; the 2-day staleness guard aborts steps 2–3 for an old recovery. Nothing in the chain touches `messages` or `plans`.
- `morning_chain_runs` claims each wake date before the expensive steps: PK (athlete_id, wake_date), status running/done/error, `claim_token` rotated on reclaim, 6-minute stale window. Running or done → skip; error or stale → reclaim.
- `lib/summarise.ts`, `lib/reflect.ts`, `lib/whoop-sync.ts` hold the former route bodies as functions; `/api/summarise`, `/api/reflect`, `/api/whoop/sync` are thin wrappers with unchanged responses. The on-mount fallbacks on Today and Coach are untouched and remain the safety nets.
- `log_insight` treats a 23505 duplicate-key hit as "already logged" (not an `Error…` string), so a Coach fallback racing the chain reads the existing row instead of retrying into the guard.
- `/debug`: "Last Whoop sync" and "Last morning chain" header lines; colours for `wearable_sync`, `morning_chain`, `timing`.

Not touched today: prompts, `lib/context.ts` block structure beyond the loaders above, the brain, tab instructions, Season/Week pages.

KNOWN GAPS

No auth
The athlete id is hard-coded in every client component and route. All app tables have RLS off and are readable and writable from the browser with the anon key (`wearable_tokens` is the one exception). `/api/chat`, `/api/summarise`, `/api/reflect`, `/api/whoop/sync` and `/api/debug/*` are unauthenticated; backfill is gated by `INGEST_SECRET` only; the webhook by HMAC only, and it does not check the payload's `user_id` against the connected account. Fine for one athlete on a private URL. First thing to fix before a second user, and the reason "build for one, architect for many" is still only half true.

Agent-loop duplication
`app/api/chat/route.ts` and `lib/reflect.ts` each implement a full Anthropic tool-use loop: stream-first call, per-turn parallel tool execution, `cache_control` on the last tool result, overload retry, thinking config, debug logging. They differ in policy — chat: Opus → Opus retry → Sonnet, atomic FINAL text emission, per-tab caps, safety-net final call; reflect: Opus retry once with no fallback, JSON final payload, pulse/deep caps, commit-now guard. Today's refactor moved reflect's loop into a lib function but did not unify the two. A shared `runToolLoop(messages, tools, policy)` with hooks for emission, retry policy and the guard is the obvious extraction; not done today to keep the chain change reviewable. Until then, changes to one loop (thinking, parallel execution, cache rules) must be mirrored by hand in the other.

`athletes.timezone` mostly unused
Added as a fallback for wake-date derivation. In practice Whoop's `timezone_offset` is present on every sleep record, so the column is read only when a sleep record cannot be fetched and by the staleness guard's "today" for the 2-day age check. The morning chain deliberately does not use it as a gate — Whoop's offset is the only clock. Two directions: drop it, or make it the source of truth for the day-name labels in the context block (`formatDate` still attaches UTC day names and assumes client-local ≈ UTC, and `getWeekStartMondayUtc` disagrees with the client's local Monday for timezones far west of UTC). Not urgent for an athlete in Europe.
